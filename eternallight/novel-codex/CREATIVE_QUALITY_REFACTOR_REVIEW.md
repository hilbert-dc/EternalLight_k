## 3. 论文使用审计

- Re3／DOC 支持规划与修订机制，但不能从数千词实验外推专业中文长篇的文学最高水平。
- DOME 的动态规划和时间记忆可借鉴；大量调用与长耗时属于原研究配置，产品必须重新验证交互预算。
- Agents’ Room 主要验证自动故事生成与任务分解，未证明多代理人数越多越好，也未证明专业长篇共创。
- Wordcraft 为专业作者定性研究，揭示声音和控制问题，不能直接转为效果百分比。
- Doshi／Hauser 的创意辅助与同质化结果均保留，避免只引用有利结论。
- LitBench 的 Reddit 偏好标签与评价器一致率不等同通用文学裁判准确率。
- LitVISTA 的给定事件锚点、英文文学和解释主观性限制写入正文；它是诊断依据，不是生成提升证据。

原始来源直接链接在主文档第 2 节；原文机制、产品假设与未来验收分开表达。

## 4. 交叉复核与整改

| 条件 | 整改结果 |
| --- | --- |
| 手动组合是否提前污染普通候选存在歧义 | 新增实验内 TrialSelectionRevision；组合不加第三生成槽，显式带回才更新普通候选 |
| 方案相同输入与现有 currentRevision 校验冲突 | 试写专属校验固定快照与实验头；普通生成保持当前版本检查，带回执行当前 CAS |
| 权限收紧只写了读／续跑，遗漏存稿与完成 | 撤销活跃 capability，读／存／complete 全部重新校验，迟到回包不得复活任务 |
| 提案选用可能覆盖作者的未采用规划 | 所有受影响普通候选头 CAS，选用产生候选和冻结审阅，编辑后重新核对 |
| 两次单产物采用可能被实现为“组合原子采用” | 明确 ChangeSetReview 是新增能力，包内引用与全部正式状态同事务；阶段与验收同步拆分 |
| 预算表达可能要求实际用量完全相同 | 固定预算上限并逐请求记录实际量，不为凑预算强制调用 |
| 只统计成功样本会夸大效果 | 全部预定运行的完成率与双方有成品的条件偏好分开报告，失败保留总体分母 |
| 原产品文档仍指向 AC-0／1 下一步实施 | 更新后续入口与阶段结论，将初始源码缺陷标为历史核对 |
| Q1／Q2 验收可能被误作第一批出口 | 验收表后添加阶段映射，首批 AC-2.1 不要求声音与文学反馈完成 |

## 8. v1.1：EternalLight 上下限机制研究与复核

### 8.1 研究范围与设计改变

从源码中整理 12 类机制、16 组证据，新增 22 个验收场景。产品路线增加 F1/F2 创作依据与取证、P1/P2 长篇规划深审与修订、N1/N2 故事单元与长期承诺；AC-2、Q1/Q2 的探索、声音、创意兑现和亮点保护相应补充。所有新增能力标为待实施。

### 8.2 独立意见、分歧与取舍

| 角色／议题 | 初始意见或风险 | 最终取舍 |

## 9. F1 实施设计门禁与落地结果

日期：2026-09-13。实施前由主代理承担架构，独立角色分别承担技术 A、技术 B／小说作者、产品经理／UI/UX，完成五角色源码复核。共同否决了把 `candidate_head_revision_id` 同时当输入与输出的方案，也否决了仅加“选用”按钮、仍在保存 Plan 时改写成正式 Outline 来源的方案。

最终不变量如下：作者选择、正式采用和 Agent 输出是三种独立状态；任务冻结 `baseTargetRevisionId`、跨章参考修订、规划修订和作者原始意图，`candidate_head_revision_id` 只负责输出 CAS；首次授权 `read_context` 保存最终实际投影及 SHA-256，后续逐字回放，同时继续检查任务版本、线程和 capability；required 目标正文、作者选定工作稿和规划依据不参与普通裁剪，放不下时失败；工作 Plan 可以指导候选，但正式采用前必须先让其 Outline 依赖成立。

已实现当前 schema 的工作版本选择 CAS、可恢复续创意图、任务输入快照、来源权威／事实适用性说明、工作 Outline→Plan 与工作 Plan→Writer 来源贯通、Electron IPC 和 React 选用／取消／“保留并按此意图继续”。没有加入旧 schema 迁移、双读或旧行为回退。

自动验证：Runtime 97/97、Agent 69/69、Electron UI 3/3、production build 通过；UI 交互用例按新产品决定移除了“无规划再次确认”，并继续覆盖输入预算、丢稿保护和编辑身份。真实模型连续三次推进、真人作者试用、Windows 与质量 pilot 仍是产品出口证据，不能由自动化替代。

## 10. P1 只读规划深审实施门禁与落地结果

日期：2026-09-13。实施前由主代理承担架构整合，独立角色分别从产品／UX、小说作者／创作质量和 Runtime／AI 可靠性审阅方案。五角色共同要求：一次 run 先冻结同一份规划材料；结构、人物、阅读体验席位使用独立新线程且顺序执行；阅读体验只作为规划顾问；席位只能读取快照、提交结构化报告和完成任务；覆盖与发现分开计算；失败保留已交付报告；综合引用原报告位置，不补造共识；只读 P1 不写候选、正文或事实。

已实现 Outline／Plan 候选、工作或正式修订的只读深审，Outline 可选择全书或具体卷，支持两席均衡和三席深度模式。Runtime 新增独立 `planning_reviews` 模块，保存冻结材料 hash、逐席检查项、任务、报告、覆盖与确定性综合；取消会撤销活跃能力，迟到读取、写入、状态更新和完成均被拒绝。MCP 的 `reviewPlanningSeat` 仅暴露 `read_context`、`submit_planning_review_report`、`complete_task`。Electron 每席轮换 capability 与 App Server 会话，失败后继续下一席并最终标记部分完成。界面展示值得保留内容、优先意见、分歧、完整报告、未检查项和旧来源提示，并明确意见不会自动采用或阻止作者保留原案。

同时收紧 F1：工作大纲与章纲可直接成为编辑和 Writer 预览依据；目标章与前文章节都显示实际修订角色；任务事实适用性依据冻结来源判断；来源指纹覆盖用途、位置、规划与正文修订；重启后持久续创意图不会被本地默认值覆盖。
