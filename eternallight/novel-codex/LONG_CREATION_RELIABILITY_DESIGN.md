# 长篇创作执行可靠性设计与评审

日期：2026-10-07。依据：实际应用《万城灯火》100章体验、保存回执、任务记录和模型请求记录。本记录由同一实施者按五个角色独立审视；不冒充独立人员评审。

## 目标与边界

目标：新章创作通过明确章数的 GenerationRun 执行；候选链顺序推进时读取新冻结输入；最终交付由模型提交可验证自检；上下文在桥接输入硬限制前压缩，超限不得重试同一请求。总字数是全书规划目标，100章是本次生成任务目标，两者分开保存。完成只以实际章回执及最终审核为依据。

非目标：自动采用、发布候选；用主机编造模型自检；通过自然语言关键词自行扩大权限；历史兼容、升级、迁移、双读双写。保持现有作者确认范围和预算的生成入口。

影响模块：Electron 同租约执行及 advisory prompt；Native 候选动作输入校验；Agent Engine 上下文目录与桥接错误；真实 Runtime 协调测试、当前 schema 测试与应用验收。

## 目标架构与实施

1. 新章与批量章节优先走 request_generation_handoff，使用真实目标章数、作者意图和当前来源。已有 GenerationRun 持久记录章回执、任务次数、预算和检查点；不能以普通对话 canFinish 替代生成目标。将这一分流置于 ordinary advisory 的前部，避免被资料修改提示淹没。
2. Native 对候选链只认可同 Work、同原始 advisory、已完成且有实际保存回执的孩子改变 candidate head。accepted head、working baseline、作者意图及工作区版本必须仍相同；其他工作和手工写入仍拒绝。旧任务的冻结来源不更新；下一 worker 重新冻结当前输入。
3. Work 决策有最终自检要求而模型仅返回文字时，Host 在原任务、线程、执行租约和预算内发出最多两次协议纠正，要求模型读取最新 read_work_status、提交 complete_task。Host 不构造 deliveryReview；仍未完成则明确协议失败，保存内容保留。普通 worker 和只选下一动作的协调不新增自检要求。
4. 模型目录的压缩阈值使用保守输入预算的60%，保留 tokenizer 差异、工具协议及下一轮任务注入空间。桥接精确输入硬限保留；该超限具有固定诊断码、400终止状态及 retryable=false，不重复请求耗空时间。自动压缩仍由 Core 在原线程执行，不创建新工作或额度。
5. 既有构建身份和策略一致性门禁保留，源代码验收使用重新构建的当前 Runtime/Engine；打包应用不是源码热更新。

## 验收标准

- 三项同源候选顺序批准并执行，后续 worker 看到实际前序候选；手工、其他 Work、采用或基线改变仍拒绝。
- 真实 Runtime + 生产 Host：模型遗漏 complete_task 时同任务纠正成功；不生成额外预算，不伪造审核；连续遗漏有界失败。
- 全100章生成目标不能在99章满足；既有生成检查点和恢复测试通过。
- 上下文输入硬限拒绝必须非重试；模型目录阈值低于硬限并有余量。
- 当前源码构建与必要回归通过；实际应用验证明确记录所用构建、操作及保存结果，不能用模拟测试声称100章实际生成成功。

## 测试阶段零兼容门禁

- [x] 无版本判断、旧字段 fallback、双读双写、迁移、回填、降级或 deprecated 路径。
- [x] 不因旧调用方、旧数据降低目标架构。
- [x] 当前生产代码、fixture、测试与文档一起更新；不改变历史格式。
- [x] 集成测试重建当前 schema 测试作品。
- [x] 数据一致性、并发授权、错误恢复及安全门禁必须验证。
- [x] 无兼容实现；无需兼容例外授权。

## 五角色实施前评审

- 架构专家：APPROVE。Native 负责来源与完成权，Host 负责协议履行，Engine 负责输入预算；不把模型提示当作唯一完成校验。不得更新旧快照。
- 技术专家 A：APPROVE WITH CONDITIONS。候选变更必须有同源已完成回执；外部修改负例和原租约额度验证是发布前阻断检查。
- 技术专家 B：APPROVE WITH CONDITIONS。协议纠正不得在租约关闭后重建任务；最多两次。真实 Runtime 测试必须覆盖自然回复而漏工具的路径。
- 产品经理：APPROVE。作者看到实际保存数量、部分完成及可继续状态；100章目标经生成入口明确确认，不以创建第一章代替目标。
- UI/UX：APPROVE。保留当前明确章数与预算的确认界面；协议错误说明已保存成果保留，不能要求作者手工处理内部技术字段。

综合结论：APPROVE WITH CONDITIONS，上述负例与集成测试通过后方可宣称修复通过。获授权兼容例外：无。

## 实施后复核

最终实现覆盖：新章生成分流与参数纠正；同源已完成候选回执的顺序审批；未执行的显式候选请求进入待交付要求；原任务、原能力及原 Engine 租约内最多两次交付协议纠正；60%输入预算的提前压缩；结构化非重试输入超限及 Core 压缩恢复；统一100章来源范围。读取 Work 决策状态使用当前任务能力凭证，不降低 Candidate 接口校验。

验证证据：

- 生产 Host + 真实 Native Runtime：方向候选→大纲候选→最终决策，四个任务、五个模型回合；后续 worker 分页读取新的冻结方向来源。故意漏交最终审核后，同任务纠正成功；Host 不构造审核，不新增预算。另三项协议测试覆盖两次上限、取消与 Native queued 状态。
- Native 候选审批：既有12项绑定与外部修改回归、新增同源完成回执与冻结来源测试通过；既有5项交付回归通过。
- Agent Engine 桥接与契约43项通过：硬限拒绝为400、context_input_budget_exceeded、retryable=false；真实下游请求数、预算请求数、预留额度都为0。Core API 的专用错误映射测试与当前 API 检查通过。
- 决策、恢复、最终回复与协议定向回归26项通过；前端 TypeScript 与生产构建通过。
- 真实 Runtime 范围4项通过，含100章启动、101章拒绝、范围不可改成99章、提案不是执行权限；作者来源13项、暂停重启恢复5项通过。重规划回归1项通过。
- 当前 Engine/Native/CLI 已重新构建，模型策略构建身份已刷新；实际应用完成当前模型连接验证，没有绕过门禁。

## 上下文恢复补充评审（实施前）

已超限的线程也要能在原线程压缩恢复。桥接的400终止响应携带 context_input_budget_exceeded 与 retryable=false；Codex API 只把这个结构化输入超限映射成 ContextWindowExceeded，普通400保持 InvalidRequest。Core既有压缩逻辑在压缩请求超限时裁掉最旧历史项后重新构造请求；不重复相同失败请求，也不重置任务额度。

影响新增：codex-rs/codex-api 的 HTTP 错误分类及测试。五角色复审：架构 APPROVE（错误语义一致）；技术 A APPROVE WITH CONDITIONS（严格诊断码，非重试标记）；技术 B APPROVE WITH CONDITIONS（正例与普通400负例测试）；产品 APPROVE（现有超长对话可恢复）；UI/UX APPROVE（无需作者手工缩短技术上下文）。零兼容门禁 PASS；未增加历史格式处理。条件：当前 CLI 必须重新构建及更新构建身份，不能跳过门禁。

## 长范围来源校验补充评审（实施前）

真实 Runtime 范围回归发现：生成入口接受100章，但 generation_author_source::history 仍把 end-start 限制为2，导致超过3章的作者来源在启动事务内被拒绝。统一使用 MAX_GENERATION_CHAPTERS 检查范围，保留所有来源、历史文本预算和原子事务校验。100章启动及101章拒绝的真实HTTP测试作为阻断验收；不增加兼容路径。

五角色复审：架构 APPROVE（唯一范围常量）；技术 A APPROVE WITH CONDITIONS（100章原子启动回归）；技术 B APPROVE（保留来源和历史预算）；产品 APPROVE（界面承诺与启动边界一致）；UI/UX APPROVE（不向作者暴露内部来源字段）。零兼容门禁 PASS。另一个回归测试沿用409断言，但当前接口对未发出的 intentRevision 有明确400参数纠正说明；按当前契约修正该断言，不改变生产校验。
