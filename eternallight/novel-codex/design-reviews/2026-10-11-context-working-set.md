# 长期创作工作集与效率证据

## 设计与责任（实施前）

根因分类：设计缺陷。按总上下文的固定软阈值维护，把必要初始资料和后来增长的历史混为一谈；传输字节不能证明成本收益。现有 Native Work、版本化 taskSources、持久 returnedCoverage 已提供任务恢复与按需原文依据，不另建状态库或强制文学流程。

Core 已有 body_after_prefix：以每个窗口的首个实际输入为基线，后续增长触发维护，模型完整容量独立保护。Engine config.compile 公开并校验 autoCompactTokenLimitScope；Host 选择增长模式，模型目录的 96Ki 变为新增历史的维护间隔，不再是包含必要工作集的总量目标。此数值仍是可校准初始策略，不宣称经济最优；不把缓存率当资料无用程度，不因缓存高取消容量保护。无 Core 修改或第二套压缩循环。

离线效率报告消费真实 rollout 的供应商累计 usage：每个 session 使用最后累计值，不累加每次累计事件；缓存属于输入，推理属于输出；缺失保持未知。报价由显式输入提供，缺失时不算费用；不猜价格。报告列出压缩次数、完整性、每个会话及整体已知用量，和传输/Engine账本分别解读。报告不写账本或认定作品完成。

复用现有按需读取与独立核验合同；摘要仅导航、原文证据按任务和版本绑定。保持暂停、授权、Work额度、原文及保存条件不变。无 schema 改动或迁移。

`npm run evaluate:context-efficiency -- report.json rollout.jsonl ...` 输出每个 session 与合计用量；可加 `--rates rates.json`，其 JSON 按 sessionId 映射 `{currency, uncachedInputPerMillion, cachedInputPerMillion, outputPerMillion}`。混合币种不合并费用，缺失缓存不假定为零。真实目录只读，不自动恢复任务或请求模型。

## 2026-10-11 追加：token是否实际有效的审计

用户原则：有效贡献无需为了数字降低而削减，优化对象是无效重复与工程性返工。仅离线分析既有样本，没有额外创作请求或调整维护阈值。

供应商账本中协调/检查15441423（84.98%），写作2729680（15.02%）。operation不等于认知作用，不能把85%全部认作浪费。1817万为多请求累计输入输出，不是1817万份独立资料。协调线程84条逐请求usage记录总量与最终累计相符，9个回合的首请求输入依次49914/83737/125143/152309/187307/209558/241479/266166/322488；未发生维护，旧过程历史持续进入后续步骤，属于有证据的上下文生命周期优化对象，但日志不能给出删除后的质量因果效果或准确浪费比例。

工具轨迹显示协调线程26次read_work_status、44次read_source_content、8次read_context。状态变化、版本校验与当前正文核验都有作用，不能单凭次数削减。5个明确拒绝返工：complete_task缺作者要求完整读取1次；chapterAcceptance超过3500 UTF-8 bytes1次；evidence_quote_not_found3次。拒绝机制有效，应降低无效请求的发生率：公开可操作的读取完成状态/前置条件、让输入契约与可存储验收文档一致、使用稳定正文位置和版本生成精确引文；不得通过放宽验收或模糊匹配伪造通过。

19章4次完全相同的read_source_content结果共16117字符，其中3次（6524+4598+4627字符）跨压缩窗口重读，可能为恢复必要资料；同一窗口重复1次仅368字符，尚不足以认定可删。这个反例说明压缩有摘要和重读成本，不能简单继续降低20%阈值。现有维护配置是修复生命周期缺口的初始方案，不是已证明最优方案。

有效性验收应以相同任务/质量标准下的保存成果、核验正确性、错误与重试、恢复资料用量和总请求费用共同判断。必要原文、真实连续性修补、版本绑定检查保留；先优化过期执行历史的常驻、协议性失败与控制空转。尚无匹配对照，因此不提供虚构的“有效token比例”或节省目标。
