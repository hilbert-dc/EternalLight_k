# 对话创作授权与接续的一致执行方案

## 目标与边界

作者一句明确创作要求应由模型理解、在该要求内组织执行并交付。讨论、提议、生成候选、采用、发布保持不同权限。模型不得凭自己的建议扩大作者范围；工程也不得把每个新章节都当作必须再次批准的任务。Host 管生命周期与真实路由，Native 管作者来源、领域权限、事务与幂等，模型组织创作；不改 Codex Core，不做历史库迁移。

原样本：隔离《雾港来信》，输入“生成第1章，约800字”。提案 proposed、无正文，后台事件 pending，错误 invalid_request。原失败保留。初步怀疑的“独立 home 导致读取失败”已被只读真实适配器复验排除：同一 thread/read 返回原线程与 1 个回合；不能据假设重做会话存储。

## 实施方案

1. 先定位失败的实际请求边界。Native 请求错误保留无请求正文的路由、阶段与原原因，后台诊断能够定位；不要将未知原因统一归为模型不可用。
2. 生命周期入口在读取、建域或启动任何执行前校验连接门禁；域内继续校验以覆盖竞争。运行、读取、恢复使用权威身份，不能从当前显示窗口推断任务。
3. 交接合同应区分“作者已明确要求的执行”与“模型提出的新范围”。前者引用真实作者消息及原意图版本，Native 核对来源、范围、暂停、费用与保存状态后准入，Host 按持久事件幂等派发；后者才询问作者。不得仅把 approvalRequired 改成 false 或让 Renderer 自动点击批准。
4. 状态以成果为准：讨论结束不能等于章节交付；提案未消费、后台受阻应显示实际原因。源任务、费用、保存回执沿同一授权链保留。

| 输入事实/权威 | 结果 | 副作用/下一步 |
|---|---|---|
| 连接正在验证或切换/Host | 拒绝新执行 | 不读执行身份、不创建域、不派发 |
| 对话历史存在/Core；Native 接续拒绝 | 保留原拒绝 | 定位 Native 路由，不重建对话 |
| 作者明确要求且有当前来源/Native+模型解释 | 在授权范围内生成候选 | 幂等交接，不采用、不发布 |
| 仅讨论或模型新增范围 | 不授予生成权限 | 如确需执行再询问作者 |
| 作者暂停/取消、未知写入 | 不自动绕过 | 核对真实状态，保留账本 |
| 接续事件重复 | 复用事务回执 | 不重复写章、不重置费用 |

五视角前审：架构 APPROVE（B02/B03/B05/B06）；技术 A APPROVE（来源与幂等不可放松）；技术 B APPROVE（公开合同回归、真实故障负例、真实应用再验）；产品 APPROVE（移除重复授权需实现真实授权合同，不能仅改文案）；UX APPROVE（主线说明真实进展、诊断按需查看）。零兼容 PASS。实现完成及实际验收前不能宣称全部落地。

## 精确根因与实施记录

真实适配器只读 `thread/read` 成功，排除先前会话 home 怀疑。原始错误定位为 `/work-execution-events/{event}/ack`：`work execution event: no actual successor Attempt or final delivery`。Native 将 completed+未消费提案视为仍需接续；Host 的 automatic 分支又直接返回 completed，因此确认失败并退避重复。新章强制批准来自 MCP 的明确返回说明，不是模型自行决定增加要求。

已实施：
- Host `executionIdentity` 在读身份前执行连接门禁；配置中未绑定引用修复继续保留。
- 经 Native 真正领取的 durableWake 不受普通 automatic completed 提前返回限制；仍校验原事件、任务、线程、租约，暂停取消及费用校验不变。
- Native 把当前合同下尚未批准的新范围提案明确返回 `blocked/generationScopeApprovalRequired`，保留 pending 事件及提案，不授租约、不错误 ack、不伪造最终交付。恢复原范围的 handoff 不进入这一分支。
- Host 的 Native 错误附带无正文的请求路由，后台日志保留限长原始原因，避免只剩 invalid_request。未发送密钥或小说正文到日志。

最小回归：Host 实际生产函数的 completed+durableWake 用例验证到达 decision，且未调用 control、新建 task 或 budget-authorization；连接门禁拒绝路径保持零 Runtime 访问；未绑定名称正负例；22 项事件消费者测试；13 项 Native 事件测试通过（含新范围待批准、已有范围接续、暂停取消、未知写入/费用、重复与并发领取）。日志 `/tmp/completed-work-wake.log`、`/tmp/handoff-entry-regression.log`、`/tmp/handoff-host-events.log`、`/tmp/handoff-native-regression.log`。

## 尚未实现：明确作者请求直接执行的授权合同

不能把新范围全部自动批准。目标实现应将模型的意图解释输出限定为 executeAuthorRequest / proposeScope，并绑定 Native 已保存作者消息 ID、意图代次、精确原文引用和目标。Native 只验证来源与明确能力边界，不按“生成”“继续”等词判断语义；模型从完整输入区分执行、讨论、假设及歧义。新章分配、工作稿生成与必要检查纳入原 Work 的结构化执行范围，沿用原授权 ID 与累计账本，禁止建立新 Run 清零额度。Native 的接续准入、提案消费、下一执行关联须在同一事务提交；重复事件读取该回执。采用、发布、范围外修改仍需相应独立授权。

需要一次性同步工具 schema/MCP 回执、Native 请求与事务、Host 消费、UI 持久恢复入口、当前 fixture 和真实应用验收；不能仅删除 MCP 的批准说明、让 Renderer 自动确认，或用请求中的作者引用直接授予超范围权限。这部分当前只完成方案，未声称已实现。因此“一句话自动生成并交付第1章”和“无重复批准”的完整目标仍未完成。

## 重启后的真实应用核对

2026-10-09：Native 构建完成；Host 合并回归 29 项通过，Native 事件回归 13 项通过。以相同隔离数据目录重启 5184 验收窗口，实际界面仍是《雾港来信》及原输入“生成第1章，约800字”，目录 0 章。未追加创作指令、未点击批准、未新建作品或修改原始数据。

只读数据库确认原事件保持 pending，claim_id、lease_id、consumer_step_id 均为空；原提案仍 proposed 且未消费。重启后的观察窗口内，日志未再出现原先的 invalid_request / no actual successor 回执失败。此证据仅证明本次空转修复的应用表现，不代表正文生成或长期恢复已经验收通过。

发现的后续界面缺口：历史回复要求批准，但重启后没有相应操作入口，显示“讨论已结束”。当前 `generationHandoff` 是 App 局部状态，切换会话时清空，历史读取未恢复。后续应由 Native 持久待办投影提供提案及状态，Renderer 只展示；不能用助手回复文本推测待办，也不能为恢复入口而自动批准。明确执行与新增提议的语义授权合同应与该投影一起实施，避免再建立第二套状态。

后审结论：本次已实现的连接门禁、持久唤醒与回执修复通过定向回归；完整产品目标 **未通过**。下一验收门槛仍是新作品一句明确请求后，应用自主生成、保存、检查并交付可打开的正文；讨论请求不写入、模型扩大范围需确认、刷新待办不丢失、重复事件不重复生成或重置账本。
