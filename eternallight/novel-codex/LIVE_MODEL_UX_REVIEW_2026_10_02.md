## 变更概览与验收

目标：使空章节开始写作、模型连接等待、候选审阅、正式稿与候选隔离以及断连恢复都具有明确、可信的反馈。

为便于审查，按以下独立阶段划分：

1. 首次写作与审阅：空章节直接生成；同步防重复；已有正文先保存精确来源；迟到读取隔离；事实未决定、保护冲突及其他采用阻碍可见。
2. 模型连接：覆盖验证、读取结果、应用的整段同步锁；连接阶段与耗时；失败重试；作者与作品隔离；IPC 双向执行互斥；账号验证整体网络请求超时。
3. 作者入口与回答：查看章节与审阅只读导航，退出账号页并保留章节选择及未保存导航检查；移除作者界面的上下文压缩入口；有上限的多行回答保持完整。
4. 任务契约：前端一次切换到 Runtime 当前 camelCase 任务字段；候选可审阅与运行中正确区分；当前章正文修订按修订 ID 去重计数。
5. 同源恢复：只核对原任务状态，保持执行所有者和原生成流程；恢复读取失败不把原生成误判为失败，不发起第二次模型生成。
6. 真实模型输出边界：模型推理 item 的首次接收检查和确定性错误的重试分类，作为独立引擎阶段处理。禁止放宽 10K 限制、截断或重写已经进入历史的内容。
7. 终态恢复反馈：状态读取失败时，正在执行的任务仍可等待或停止；已结束的任务退出“正在恢复”提示，保留原错误和耗时，并允许新指令。

## 追加设计：单一编辑区与章节发布

用户进一步明确：草稿、正式稿和审阅区的概念过于复杂，希望只保留编辑区，然后发布章节。

当前目标界面收敛为“编辑正文 → 发布前检查 → 发布章节”：编辑器始终存在，状态只表达“未发布 / 有未发布修改 / 已发布”；已发布内容与修改对比收在按需打开的版本区域。总览只显示已发布内容；章节还未发布时显示已保存正文，不再提供另一个来源切换入口。

发布前可保存当前编辑，检查必须绑定该次保存的准确章节版本。作者确认事实、保护冲突和实际发布，是同一个发布流程中的决定；不把模型建议直接当成设定。已分析且同源的事实批次必须纳入检查；没有分析的手写正文可以由作者明确确认“本次仅发布正文，不新增故事设定”，无需强制连接模型。读取失败或仍在交付的创作任务不能被当作无事实正文发布。

此阶段五角色预审为 `APPROVE WITH CONDITIONS`，冻结的前端实施后五角色复核为 `APPROVE`，无剩余 P0/P1。条件包括保存与发布回执的只读恢复、同步防重、跨作品和章节隔离、检查关闭保留决定、正文再编辑后旧检查失效，以及整章发布覆盖标题、顺序和删除。Runtime 的保存版本与发布版本仍保留内部职责，不修改当前 schema 或添加旧格式兼容。内部发布载荷全选当前章节的全部场景 ID，使用现行整章采用合同覆盖标题、顺序和删除；界面不提供部分发布选项。

## 知识任务推理策略的独立后续阶段

真实失败来自模型自生推理，不能通过裁剪故事上下文宣称解决。评估了知识分析单独使用较低推理强度的方案；[DeepSeek Responses API](https://api-docs.deepseek.com/api/create-response/) 支持 `reasoning.effort`，但当前引擎没有此能力声明与认证，当前模型目录也没有按任务隔离的入口。

直接把 `low` 加入共享模型目录会影响 Core 在模型切换与恢复时选择的默认档位，可能一起改变正文创作。五角色批准本轮收敛范围：完成输出接纳修复，不临时绕过能力认证。后续拆为两阶段：先声明与真实认证 `reasoningEffort`，更新环境指纹；再为冻结的知识操作建立独立 `CODEX_HOME`、模型目录和显式档位，验证新线程、恢复以及知识任务后的正文创作均保持各自设置。该策略本轮没有写入生产配置，也不保证模型推理必然低于上限。

## 已知体验限制

- `childWait` 曾在一次验证中失败，修复后新指纹认证通过；这说明存在波动，不能把单次通过推广为所有高级能力稳定。
- 真实模型仍可能在自由对话中只返回正文。作者需要生产候选保存回执才能判断正文是否已保存。
- 原真实候选包含时间矛盾与认知边界混淆；定向修订能够修正，但模型输出仍需作者审阅。
- 生成与知识提取是两个实际阶段，首章正文交付耗时不等于完整知识审阅准备耗时。
- 第二章知识提取前两次失败，修复后的第三次真实尝试完成；模型推理仍可能超限，新的接纳检查负责明确阻断并避免无效重试，不保证每次分析成功。
- 真实模型最终答复仍会包含内部 ID 与字段名，精简作者侧答复仍有改进空间。

### 发布事务的附加一致性门禁

实施后交叉复核发现：省略内部场景选择会使已确认的模型事实在原生采用中被拒绝；知识分析又不会推进作品版本，单独检查作品版本不能阻断旧检查。因此独立批准一个小型原生阶段：创建检查时从已验证的分析批次生成规范绑定，并拒绝伪造或冲突的绑定；采用事务在落盘前核对同一正文的当前知识头。未分析正文仍允许作者明确确认后发布，旧版本的分析不会强制应用到新正文。提交中的可选批次标识若出现，必须与规范检查绑定一致。复用当前字段，不添加 IPC、schema 或旧格式读取路径。

前端发布专项验证覆盖：创建检查成功后读取失败不重复创建、保存及发布回执精确核对版本、6 项同源事实逐项决定且重复条目不重复显示、异作品读取拒绝、同 ID 不同事实拒绝、确认前分析更新重新准备、整个确认期禁止改动/关闭，以及 A→B→A 的迟到结果不能写入新操作。常驻编辑器的未保存标题/正文、光标方向/滚动、128 条书签上限、主题对比度与场景新增/修改/重排/删除均完成快照验证。

原生冻结后通过 `just test --profile default` 验证 story-core、story-runtime 的库测试以及 chapter_acceptance、chapter_acceptance_http、event_review_integrity、workflow、proposal_selection 测试：196/196 通过，0 跳过。覆盖伪造批次、手写检查后出现新分析、旧批次全部拒绝仍须阻断、整章选择与事实证据、标题/排序/删除和失败事务不写入。Story Runtime 重建成功，最新运行窗口已实际完成上述发布。原生阶段五角色实施后复核为 `APPROVE`，无剩余 P0/P1；前端与原生发布阶段总体门禁 `PASS`。Windows 本轮未实机运行。

收尾执行仓库要求的 `codex-rs/just fmt` 成功；本轮涉及的 novel 原生发布、任务读取及引擎输出边界文件通过定向 `rustfmt --check`，`git diff --check` 通过。测试均在最终格式整理之前完成，按仓库要求未在格式整理之后重跑。体验窗口保留在第二章已发布的编辑区；合成作品隔离于作者原有作品。

## 滚动黑色空白修复：设计前评审

用户截图与真实窗口均复现：章节展开多个附加区域后，滚动会带动外层页面，整排侧栏、正文和对话栏上移，下方露出黑色空白。根样式仍写死 `#111214`，浅色主题仅覆盖 body 和应用内容；workspace 和侧栏只有最小高度，未建立受视口约束的独立滚动边界。

方案：根背景使用主题色；禁止根页面的过度滚动；应用壳固定于当前视口，workspace 的网格行允许收缩，三栏在受约束的高度内各自滚动，阻断滚动继续传到外层。登录页面仍保留正常文档滚动，不改变模型、发布流程和数据。

| 角色 | 设计前结论 | 检查要求 |
| --- | --- | --- |
| 架构专家 | APPROVE | 仅修正 Renderer 布局边界，不修改 Runtime 或 Electron 安全策略。 |
| 技术专家 A | APPROVE | 栏目内容不能撑大根页面；长侧栏、正文、对话分别可达末尾。 |
| 技术专家 B | APPROVE | 真实 Electron 验证短窗口、常规窗口及两种主题，增加对应快照。 |
| 产品经理 | APPROVE | 翻页不会把整个工作区带出窗口，不丢失正文或作者决定。 |
| UI/UX 设计师 | APPROVE | 滚动到底不露黑色背景；小高度窗口内侧栏仍可滚动访问。 |

零兼容门禁：无接口/schema 修改，无旧字段兼容、迁移、双读双写或回填；修复当前界面布局。范围为样式及布局回归测试。
