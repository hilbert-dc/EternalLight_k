# 任务管理优化：读取与控制一致性

## 目标与证据

Task / Step / Attempt 的持久状态仍由 Rust 管理，不重做调度器。当前检查确认
Renderer 的列表读取失败会清空任务，首屏轮询和控制刷新分别写入同一状态，
分页只依赖异步 React busy，控制返回缺少作品生命周期隔离。

本轮修复这些已确认问题，不将 UI 回归通过等同于全部任务语义或理想架构完成。

## 实施设计

- 独立任务列表 Hook：同一作品生命周期最多一个读取在途；刷新合并并使旧分页
  响应失效。分页仍使用 Rust 游标，失效后重新读取第一页，不拼接不同水位。
- 初次读取、最后成功结果、读取错误分别表达。失败保留已有任务并禁用控制，
  显式重试只读取，不创建任务。不同作品或 A→B→A 的旧结果不得重新出现。
  缺少 Runtime 读取接口时明确显示不可用，不冒充无任务或无限加载。
- 运行中的持久任务也触发轮询，不只依赖当前 Agent 的前端标志。
- 控制使用同步互斥及生命周期身份。写入后刷新任务；已提交控制与读取失败
  分开显示，读取失败不伪装为控制失败。跨作品返回不修改当前界面或释放新操作。
- 正式采用撤销及 GenerationRun 的业务门禁保持原领域契约。

## 五视角实施者自检（非独立专家评审）

架构：只抽离读模型，Rust 为唯一状态权威。技术 A：同步互斥、响应代次与生命周期
隔离；技术 B：真实 Electron 的延迟、失败、分页、作品切换回归。产品：读取错误
不是任务不存在，控制失败不会被后台读成功掩盖。UX：加载/读取失败/陈旧结果明确，
作者可重试，错误时禁止使用旧任务控制。结论：按上述条件实施。

零兼容门禁：不增加旧 schema、旧接口、fallback 或双轨；同步更新组件及测试。

## 验收

真实 Electron 验证读取失败保留任务、初始错误可重试、同帧重复分页互斥、刷新
与分页交错、失效游标重新读取、A→B→A 隔离。构建、现有任务 UI 和 Host 回归。
完整任务暂停/恢复/取消业务条件仍由已有 Rust 与 Host 测试验证。

## 恢复执行期间的控制（实施设计）

生产 `resumeWorkTask` 的 Promise 覆盖后续模型执行，而不是仅覆盖恢复事务。
将整个等待期间作为所有任务控制的互斥区，会使作者无法暂停或取消刚恢复的任务。
Renderer 分离两个句柄：长执行等待槽与短控制槽。恢复等待期间允许暂停/取消，
短控制之间仍同步互斥；不允许重复恢复、撤销或编辑，并继续由 Rust 判断状态与版本。
UI 的 pending 只是请求句柄，不是领域执行状态，不在本地将任务改成 running。

- 请求按作品生命周期隔离；迟到的恢复回执不能清除新控制的 busy 或错误。
- 同任务取消已确认后，原恢复请求的退出错误不覆盖取消成功，包括执行先退出的顺序；
  取消其他任务和暂停不掩盖当前任务的真实执行错误。
- 控制成功与随后读取失败分别呈现。失败请求也刷新持久任务，核对可能存在的部分执行；
  刷新只读，不自动重发控制或恢复。读取失败继续保留旧结果并禁用控制。
- 回归覆盖恢复悬挂时暂停/取消、同帧重复控制、取消与恢复回执交错、失败后的状态核对、
  控制成功但作品刷新失败，以及跨作品迟到响应。

五视角实施者自检（非独立评审）：架构保留 Rust 唯一权威；技术 A 分离请求互斥与
执行状态，技术 B 通过真实 Electron 延迟回执验证；产品保留运行中停止权；UX 明确
已确认操作与读取失败。零兼容门禁：不改领域接口、schema 或模型调度，不增加旧路径。

## 不同任务错误的逆序回执（实施设计）

补充检查发现：恢复已报告执行错误、但仍在核对持久状态时，取消另一项任务
会在请求入口无条件清空错误。此前回归只覆盖另一任务取消后恢复才失败的顺序。
错误归属于当前作品生命周期内的具体请求；不同目标的新控制不清除原错误，
同目标重试可以清除。确认取消只清除其捕获的恢复请求所报告的错误，不能清除
无关请求的错误。这里只记录 UI 提示的归属，不复制 Rust 执行状态或自动重放。

五视角实施者自检（非独立评审）：单一领域权威不变；同步记录错误来源防止
反向竞争；真实 Electron 覆盖失败先到、另一任务取消后到；作者仍能发现原任务
执行失败。零兼容门禁：不改接口、schema 或调度，直接调整当前 Hook 与回归。
