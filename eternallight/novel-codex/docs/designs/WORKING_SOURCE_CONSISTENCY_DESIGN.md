# 作者工作依据与任务来源一致性

2026-09-28 · S2/S3、C03–C05 · 实施者自检，非独立专家评审。

## 问题

作者在工作区选定正文或规划的“后续依据”后，当前选择只供工作区显示及
`save_continuation_intent` 校验。Task 输入冻结的是对象候选/确认头，
Writer Context 默认读候选头；因此选定旧修订后，新候选头可能悄悄成为模型
输入。选定依据在任务执行中改变，也不会像对象头变化一样使任务失效。
新候选写入后，选定依据可能还停留在旧修订，下一次继续又会读取旧内容。
这直接破坏“改稿后可靠接续”，不属于历史版本兼容问题。

## 当前版本目标契约

1. 工作依据是作者明确选中的不可变修订，不是正式采纳。当前 schema 中的
   `revisionId + selectionRevision` 共同构成 CAS 选择状态。选择的修订必须
   属于当前作品及对象；可选择该对象的历史修订，但不能跨作品或换对象。
2. 任务创建时，连同候选/确认头冻结所有当前工作依据。任务读取、写入和
   完成前检查选择是否改变；在途任务自己的检查点可原子推进它所占用的
   工作依据，其他任务因来源改变而失效。来源摘要也包含选择状态。
3. 非自动运行的任务和作者预览以“显式选择 → 已确认 → 当前候选”为读取
   顺序。连续 GenerationRun 有自己的工作稿检查点，优先遵从其冻结运行
   来源；不会被另一个 UI 选择暗中改写。所有读出的候选/确认/选定来源
   标明实际身份，不把历史工作依据称为 Canon。
4. Writer 的当前章与可见前文、Planner 的 Brief/Outline/Plan 输入均使用
   上述选择。依然受原有 POV、章节、场景、字节预算和来源权限裁剪。
5. 选定依据上产生新候选检查点时，同一候选写事务推进对应选择版本；
   任务的后续检查点使用自己的新修订，原始输入修订作为来源证据保留。
   作者直接编辑当前选定候选也按相同 CAS 推进；若所选历史修订并非当前
   编辑来源，不自动改写选择。旧任务不得借此覆盖后来的作者选择。
6. 对话修改和连续生成仍只产出工作稿，不自动确认正文/Canon，也不
   增加第二个调度器或旧接口兼容层。

## 实施顺序与验证

- 直接修改当前建库 schema 中任务输入快照、SourceWatermark 与事务逻辑；
  不增加旧库升级或双读路径。任务所用来源写入现有 manifest/Context Pack。
- 在真实 Router/SQLite 测试中建立旧候选、作者选择、更新候选、生成任务、
  Context Pack、保存部分/完整检查点、改变选择、迟到输出与进程重开场景。
  核对来源 ID、写入 CAS、选择版本、任务失效和没有半提交。
- 对 UI 的来源标签/错误状态、类型和 Electron 任务交接同步更新。继续保留
  正文、计划、候选知识、正式采用之间的权威边界。

## 评审门禁（实施者视角）

- 架构：任务输入快照属于小说领域；Codex 内核只执行，工作依据不进入内核。
- 可靠性：所有选择与候选头的比较和推进在同一 SQLite 写事务完成；
  任务输出重试走现有回执，不双写。
- 实现：当前 schema/接口/类型/fixture 同步更新；无版本探测、迁移或 fallback。
- 产品：作者“选用这版继续”与模型实际读到的内容应可逐修订核对。
- UX：来源标签区别正式稿、候选稿和作者选定的历史工作稿；错误不能吞掉
  在途任务已写检查点，也不能谎称已经采用。

实施者检查不等于五位独立专家已评审。S1–S5 的真实模型、文学质量、
大作品性能和双平台完成条件不因本项测试通过而被视为完成。

## 当前落地边界

已将选定修订与选择版本纳入任务输入快照、来源摘要和同事务写入门禁；
Writer/Planner Context、普通任务的原文扫描与文本索引读取相同的选定来源。
连续运行与冻结来源的提取任务仍读各自的候选检查点。作者中途改选会使旧任务
读写失败；任务自身的检查点原子推进选定工作稿，不自动正式采用。

结构化知识仍以当前候选正文建模，不能把它谎称为历史工作稿的知识。
当选定/已确认文本与已建模候选来源不同，Context 仅保留来源匹配的事实与
知识条目，将不匹配的建模源标为 `model_pending`、覆盖标为不完整；任务结构化
查询拒绝混用，包括 Writer 对当前章的查询：即便结构查询只覆盖前章，也不能
因为前章范围为空，就把尚未建模的当前选定稿报告为“空结果且完整”。承诺及
提案只保留证据引用与选定来源一致的条目。
这是一项保守安全门禁，不等于已经实现“对任意历史修订建模并复用知识”。

任务输出另存 `working_base_revision_id` 并在输出引用中回传
`workingBaseRevisionId`；`parent_revision_id` 仍只表示候选 CAS 链，不再
被误用为历史工作稿的创作依据。尚需单独完成：历史工作稿
的按需建模与来源匹配的完整知识投影；真实模型 C03–C05 联合旅程、文学评价、
长篇规模与 macOS/Windows 验收。本切片不宣称 S2/S3 或整体完成。

## 2026-09-28 补充：检索 cursor 的来源失效与请求错误

当前中文检索回归暴露：cursor 的单一摘要同时包含查询形状与当前工作来源。
作者改稿后用完全相同的查询继续翻页，服务端只能看到摘要不匹配，返回
`invalid search cursor`（400），而不是来源已变化（409）。这会让调用方把
可恢复的重新查询误判为请求格式错误。修正目标是把查询形状摘要与来源摘要
分别冻结在当前 cursor 中；形状不符/篡改仍为 400，当前来源失效为 409，
快照变化仍为 409，旧 cursor 不得继续读取新来源的下一页。

实施者门禁：只修改当前 cursor 契约及消费端，不保留旧格式解析；当前
Schema 不变。来源摘要不构成模型可修改的权限，检索仍须在领域层检查。
Runtime 测试使用同一查询参数分别证明“改稿导致来源过期”和“换查询导致
无效请求”，Core 定向测试复核重建索引后的失效。此处没有 UI 改动；浏览
重试应明确重新从第一页查询，不能自动重放旧 cursor。该切片不等于
历史工作稿已完成按需建模，也不改变 S1–S5 总验收范围。

实施后复核：cursor 现在分别携带查询形状摘要和来源摘要；改稿后沿旧 cursor
翻页返回 `StaleSearchCursor`（HTTP 409），换查询参数复用 cursor 仍返回
400。中文检索 Runtime 用例先复现旧 400，再验证新 409/400 分界；
`runtime_http_tests` 20/20、Core `--lib` 157/157 通过。已分批运行当前
全部 17 个 Core 集成测试二进制和 28 个 Runtime 集成测试二进制，均通过；
native 全 workspace/all-targets 严格 Clippy、`cargo fmt --all`、仓库
`just fmt` 和 `git diff --check` 通过。没有迁移、旧格式双读或 UI 调整。
