# 知识提交的确定性拒绝与恢复

2026-09-28；实施者自检，不组织独立专家评审。

## 证据与目标

真实改稿/建模验证中，错误知识载荷被 Runtime 拒绝，之后修正提交和任务完成均已
持久化，但第一次调用仍留在 accepted。引擎正确地将 accepted 视为结果不明，
所以任务完成本身不能解除这条操作的恢复义务。

目标是记录有证据的拒绝，不把所有错误或终态任务里的未提交请求批量当作失败。
原引擎对账已支持 rejected，无需修改 Codex 内核或增加第二份任务状态。

## 本次实现边界

- 当前 schema 给操作账本增加 rejected 状态；无旧库迁移或双读。
- 知识发布的 validate_payload 在纯校验阶段返回 InvalidContent 时，在同一事务
  写 rejected 并提交，再向调用者返回校验错误。此处尚未写实体、断言或知识头。
- rejected 无候选成功回执，不自动确认任何作品内容；引擎使用既有操作身份构造
  拒绝证明，并将该请求视为 terminal/rejected，而非 committed。
- 同调用身份不能在拒绝后再次执行。改正参数必须使用新调用身份；复用旧身份且
  改 hash 仍是幂等冲突。绑定失败时清除内存中之前的绑定，避免残留被下一调用误用。
- Storage/CorruptState、失败提交、校验前数量上限、跨来源校验及其他操作的错误
  不在此次确定性终结范围，仍保守保留原状态。不能由 HTTP 400/500 一概推断结果。
- 重启前已经提交的候选仍通过原 committed 回执恢复；历史错误不从新成功提交反推。

## 回归设计

1. 真实仓储发布错误载荷后重开数据库，确认 rejected、空 receipt、批次完全未改变。
2. 同身份重放拒绝，篡改 hash 冲突，新身份正确提交成功并保持原拒绝记录。
3. 原候选发布、事务回滚、分页冻结和成功重放回归保持通过。
4. 宿主恢复索引消费 rejected 后终结该请求，不伪造内容提交；accepted 的保守路径不变。

本次不修改 UI、模型配置和真实小说，不修补之前临时数据库；新的当前 schema
测试库从空环境生成。自动调度和完整连续创作旅程仍须单独验证。

验证结果：仓储 recovery_ledger 5 项、Runtime scoped_revision 5 项、宿主 startup
reconciliation/拒绝恢复 5 项通过；story-core 全目标严格 Clippy 通过。
此次未重跑真实模型或修改历史临时库，不将先前 accepted 记录伪装成已修复数据。
