# Novel Codex 产品体验优化方案

日期：2026-10-01。面向产品与工程实施，服务于“对话驱动、可控迭代的持续
创作系统”。本方案关注作者从阅读、讨论到修改、审阅和继续创作的操作
闭环，不更换 Codex 内核，不再次建设平行任务系统。

## 产品负责人视角

本轮由两个独立 AI 子 Agent 分别承担 Codex 与 Cursor 产品经理分析视角，
主实现者综合方案并实施。没有两家公司真实员工参与，也没有官方背书。
Codex 视角负责执行、对话与结果可信；Cursor 视角负责文档、上下文与
审阅效率。分析角色不是产品运行时的新 Agent，也不扩大供应商测试授权。

官方资料提供交互参考，不是当前工程实现证明。Codex 的长任务文档强调
清晰结果、完成条件和运行中调整，并说明目标不会扩大访问权限；本产品
借鉴这些控制原则，不要求作者使用工程命令。[长任务文档](https://learn.chatgpt.com/docs/long-running-work)。
Codex 的本地审阅将查看差异与修改、撤销等决定分开；本产品借鉴可检查
结果，而不是把 Git 操作直接搬给作者。[审阅文档](https://learn.chatgpt.com/docs/code-review)。
Cursor 的侧栏 Agent、可恢复检查点和运行中跟进体现文档协作与安全迭代；
小说需要对应正文修订和作者采用，不能把自动应用代码等同于自动采用
创作内容。[Cursor Agent](https://cursor.com/docs/agent/overview)。

## 共同产品原则

- 中央是作品，右侧是对话。技术日志、审计和认证信息按需展开。
- 作者意图是主入口；结构化表单是可选的精确编辑方式，不是必经流程。
- 讨论完成、候选保存、正式采用和知识确认分别显示，不共用“已完成”。
- 输入草稿与模型执行门禁分离；阻断必须说明原因和下一步，不吞掉输入。
- 没有默认请求、token 或任务时长额度；保留统计、停止、供应商故障和
  精确授权。权限续期须单独设计，不能用无限有效权限代替。
- 当前源码、当前 schema 和当前接口一次性实现，不投入旧版本兼容。

## 第一阶段对话草稿可编辑

当前 `src/App.tsx` 的 Composer 共用一个 `disabled` 条件控制输入区和
发送按钮。中央文档未保存、模型不可用、等待模型交互都使输入区不可编辑；
主要提示藏在 placeholder，无法支持作者先记录下一步想法。这里是源码
可直接确认的交互阻碍，不需要推测供应商或存储故障。

### 交互与边界

1. 有当前作品时，文档未保存、模型不可用、等待模型回答期间仍能输入
   对话草稿。没有作品时不制造无归属草稿；改稿来源正在校验或已绑定
   到运行中任务时保留原有输入保护。
2. 文档未保存时显示“中央文档有未保存修改。保存后即可发送。”；模型
   不可用时说明先完成连接配置或验证；等待交互时说明先处理本轮问题。
3. 发送和运行中追加仍使用完整阻断条件。Enter 在阻断期间只阻止提交，
   不发请求、不清空草稿；Shift+Enter 换行，输入法组合输入不发送。
4. 提示可由辅助技术读取，不只用颜色。恢复可发送时提示消失，草稿保留。
5. 不自动保存、采用或转换任务，不修改领域来源绑定，不做隐含权限续期。

### 实施前检查

沿用用户此前取消外部技术评审的安排，由主实现者检查五个维度；两个
产品角色提供分析，不冒充独立技术或设计人员签字。

- 架构：只分离 Renderer 输入能力和发送门禁，主进程与 Runtime 不变。
- 技术 A：保留主进程权限、未保存保护和同步提交防重；没有模型调用扩权。
- 技术 B：同步更新实际 App 夹具、改稿来源回归及界面快照。
- 产品：降低写下一条指令的阻力，不以“可输入”暗示“已发送”。
- UI UX：采用邻近的文本状态，保留键盘、中文输入法和草稿；不新增弹窗。
- 零兼容：没有版本探测、旧字段转换、数据迁移或双轨入口。

验收覆盖：未保存、缺少可用模型、等待交互、恢复可用、正常发送与追加、
快速 Enter 防重、Shift+Enter、输入法组合输入，以及改稿来源校验保护。

### 作者回答提交可靠性

Codex 产品角色确认另一项 P1：App 传递 `void resolveUserInput(response)`，
丢弃实际提交 Promise，回答卡因而提前按成功处理。同步修复为传递原回执，
提交中保护答案、防止快速重复提交；失败显示就地错误并保留回答，成功
才清空或关闭回答卡。对话草稿不作为此回答消费，也不清空。

沿用同一 Renderer 边界，不修改模型或权限协议。用真实 App 的延迟提交、
失败与再次提交夹具证明等待期间只有一次请求、答案保留、错误可见，
成功后回合继续且独立对话草稿仍在。

## 推进顺序

### 全量实施边界与实施前检查

本轮按中央文档、对话恢复、事件归属、独立引擎续期四个互不重叠的代码
作用域并行实施，主实现者负责 Novel 任务凭证续期和最终集成。沿用取消
外部评审会议的授权；以下是实施者的检查，不冒充真人专家签字。

- 架构：生成、候选编辑、正式采用分层；恢复读取不重建执行任务。
- 技术 A：续期只由持有作者身份的主进程发起，绑定原任务、线程、模型、
  目标和当前来源，事务内检查有效、未撤销及原有效期；每次仍是有限凭证。
  模型会话续期需重新解析可信且有效的能力证据，不修改旧证据有效期。
- 技术 B：分别覆盖界面旅程、迟到事件、刷新故障、长任务跨越原有效期、
  撤销竞态与范围变化。执行统计和恢复账本不因续期重置。
- 产品：生成停留可审阅候选；作者显式采用才推进正式稿。刷新失败只重试
  读取，任务停止即时撤销续期，不把失败伪装成成功。
- UI/UX：中央提供正式、工作、差异视图；就地说明加载、错误、来源和采用
  状态；按稳定场景身份恢复编辑位置，保留草稿与键盘操作。
- 零兼容：当前协议一次性同步生产代码、类型和夹具；不增加迁移或双轨。

续期不授权新作品、新模型、新目标或扩展工具；已经过期、被停止、来源
变化的任务必须按恢复流程重新建立授权，不复活旧凭证。

1. 完成本文第一阶段并验收，再统一候选、正式、工作依据的状态定义。
2. 修复 P0 的单章生成采用闭环，同时提供最小正文审阅和差异入口；不在
   作者尚不能可靠检查结果时建设更多自动生成按钮。
3. 校正事件归属、执行与同步状态、线程恢复和预览状态，使恢复只做恢复。
4. 在前述控制可信后实施同范围权限续期，再验证长任务持续运行。
5. 补齐场景位置恢复、信息密度和空态引导，做实际作者端的完整旅程验收。

完成标准是：作者从一句指令得到可定位的候选，能检查变化、修改并采用，
失败能在正确边界恢复，离开后能找到同一作品和对话。不能用界面相似、
模型请求成功或所有工具可调用来代替这些结果。

### 采用契约补齐

不是仅把“采用”按钮改成更好看的按钮：后端现在实际执行作者的场景
选择。全选候选场景采用整章，包含标题、章纲来源、重排和删除；选择
部分场景只合并所选变化，保留其他正式场景及正式标题、来源。首次部分
采用只标记本地依据，不声称整章已经符合候选章纲。

原候选修订保持不可变，可对剩余变化再次审阅和采用；撤销恢复前一正式
修订。未知或重复场景、跨章节、锁定场景违规、空选择及来源冲突拒绝
写入。场景采用和知识确认仍是分别校验的决定，不能确认未选场景的事实。
作者 UI 的完整审阅字段纳入当前契约，没有为旧接口增加兼容分支。

### 交互密度与边界

已结束的工作默认折叠为历史，不把大量完成卡放在正文上方；运行中任务、
待回答和失败仍可找到。明暗主题沿用统一颜色变量并检查文字对比度。
普通发送不新增原生确认弹窗，没有默认请求数、token 或任务时长额度；
供应商错误、危险工具审批、作者停止和有限安全凭证仍然独立处理。
