# Novel Codex 工程规则

## 当前阶段：测试与快速迭代

本工程处于测试阶段，代码修改以验证目标架构和理想产品体验为第一优先级。

具体决策与强制评审清单见 [TEST_STAGE_ENGINEERING_POLICY.md](TEST_STAGE_ENGINEERING_POLICY.md)。设计评审使用 [DESIGN_REVIEW_TEMPLATE.md](DESIGN_REVIEW_TEMPLATE.md)，设计前和实施后都必须逐项检查。

- **兼容性是当前阶段的明确非目标。** 不为旧版本代码、旧 IPC 契约、旧数据库 schema、旧本地测试数据、旧 fixture、旧配置或旧 UI 行为设计、实现、测试或保留兼容层。
- 允许直接调整接口、数据结构、事件模型、组件结构和交互流程，并同步重写 fixture 与测试数据；测试数据库和测试项目默认可直接重建，不编写旧版本升级、回填、双读双写或降级逻辑。
- 优先实现清晰、完整、可演进的目标状态，避免为了短期兼容引入临时分支、重复抽象或永久保留的 deprecated 路径。
- 发生有意的破坏性调整时，同步更新类型、测试、架构文档和设计评审记录，确保工程处于一致的可运行状态。
- 评审和实施计划不得把“兼容旧版本、迁移旧数据、保留旧入口”列为要求、风险或后续待办；如果旧兼容代码阻碍目标设计，可以直接删除。
- 只有项目负责人在具体任务中明确提出兼容目标时，才允许投入兼容或迁移工作；该例外仅对该任务有效，不改变本规则。
- “不考虑兼容性”不等于降低工程质量：仍必须保持 Electron 安全边界、Runtime/Codex 环境隔离、IPC 输入校验、密钥安全、跨平台路径处理、当前 schema 的数据一致性和必要的自动化测试。
- 仍需遵循五角色设计评审门禁：涉及代码、配置、接口、数据结构、构建或 UI 的修改，先按 `DESIGN_REVIEW_TEMPLATE.md` 完成方案和架构专家、两位技术专家、产品经理、UI/UX 设计师评审，再实施。

## 目标取向

以“理想态”为目标进行设计和实现：优先解决根本问题，保持边界明确、状态可追踪、当前版本失败可恢复、界面可理解；不要为了假设中的历史调用方或历史数据牺牲当前工程的整体一致性。

本文件的测试阶段兼容性规则优先于项目内产品文档、历史评审记录和旧实施计划中的兼容或迁移要求。
