# Novel Codex 测试阶段工程策略

状态：当前有效 · 适用范围：整个 `novel-codex` 子项目

## 决策

当前开发阶段直接建设目标代码结构，只保留一套当前合同，不承担任何历史兼容责任。接口或 schema 调整在同一改动中同步全部调用方并删除被替代的实现，不新增临时兼容层、过渡适配、双轨运行或“以后再清理”的旧分支。

- 只支持当前代码、当前 schema、当前 IPC/API、当前配置和当前 UI。
- 明确隔离且可丢弃的测试数据库、测试作品、fixture 和开发样本可删除并重建；仅位于本地或开发目录不代表可丢弃，来源不明的数据不按测试样本处理。
- schema 变化直接修改当前建库逻辑和测试数据，不写为识别或适配历史程序、schema、接口或数据格式而设的升级、回填、降级、双读、双写或版本探测。
- 接口变化直接同步 Runtime、Electron、Renderer、类型、测试和文档，不保留旧契约入口或历史兼容适配器。
- 历史产品文档和评审记录中的迁移、兼容、旧版本保护要求仅是历史记录，不得转化为实现项、风险项或后续待办。
- 只有项目负责人在具体任务中明确指定需要兼容的对象与版本时，才能增加兼容工作；该授权仅对该任务有效。

作品修订、并发比较与交换（CAS）、来源有效性、执行代次和当前格式校验属于当前正确性要求，仍须执行；识别并拒绝不支持的格式不等于为历史格式提供兼容。

真实作者原作、手工维护的设定、确认记录及其引用素材不因测试阶段、schema 调整或减少自动建模而取得删除或覆盖授权。验收使用隔离副本；涉及原始作者数据的操作遵守既有授权和范围。资料保护通过保留原始资料、隔离副本及当前版本备份恢复落实，不得据此增加历史 schema 迁移或兼容读取。

## 设计评审门禁

每次设计评审和实施后复核必须回答以下问题：

1. 方案是否新增了用于历史兼容的版本判断、旧字段 fallback、双读双写、迁移、回填、降级或 deprecated 路径？如果是且不满足第5项的明确例外，结论为 `BLOCK`；当前修订、来源及并发校验不属于此项。
2. 方案是否因为假设中的旧用户、旧调用方或旧数据而降低目标架构清晰度？如果是，默认 `BLOCK`。
3. 破坏性调整是否一次性同步更新了生产代码、类型、fixture、测试和现行文档？如果否，默认 `BLOCK`，避免半迁移状态。
4. 所谓“兼容问题”是否其实是当前版本的数据一致性、错误恢复、安全、并发或跨平台问题？这些仍须解决，但不得包装成历史兼容层。
5. 如果任务确实包含兼容实现，是否引用了项目负责人在当前任务中的明确授权？没有授权即 `BLOCK`。
6. 涉及删除或重建时，是否确认对象为明确隔离且可丢弃的测试数据，并保护真实作者资料？不能确认时不得据本策略执行删除或重建。

评审结论中不得出现“稍后补旧版本兼容”“保留双轨以降低风险”或“先写迁移以防万一”等待办。实现后发现无授权的兼容代码，应直接删除后再批准。

## 完成标准

- 当前版本从空环境初始化成功。
- 当前 schema 和当前接口的自动化测试通过。
- 破坏性调整后的所有调用方一次性完成更新。
- 被替代的旧实现、旧入口及过渡分支已清除，不以暂时保留双轨作为完成状态。
- 没有为历史格式新增代码、测试或发布要求。

以上标准不免除当前版本的安全、可靠性、数据一致性、失败恢复、可访问性和 macOS/Windows 跨平台要求。
