# 创作工程架构规则

状态：强制执行。适用 `novel-codex`、`agent-engine` 及由本产品需求引起的 Codex Core 改动。小说、漫画、动画共用这些边界，不共用固定创作步骤。

本文件是职责与改动规则的唯一正文。产品目标及取舍见 [理想架构](novel-codex/IDEAL_ARCHITECTURE.md)与[演进路线](novel-codex/docs/designs/CODEX_CREATIVE_EVOLUTION_ROADMAP.md)，通用执行设计见[自主创作3.0](novel-codex/docs/designs/SIMPLE_REQUEST_AUTONOMOUS_CREATION_DESIGN.md)；当前测试阶段继续遵循 [零兼容策略](novel-codex/TEST_STAGE_ENGINEERING_POLICY.md)。历史方案、测试样例或现存越界代码不能作为新增越界的理由。目标文档不直接改变现行生产合同；规则冲突必须先在改动评审中消解，不能各层自行解释。

## 1. 各模块负责什么

| 模块与实际位置 | 必须负责 | 不得负责 |
| --- | --- | --- |
| 主模型、临时方法与子任务 | 理解原话；选择阅读、创作、检查、修订与协作；组织可变计划；解释结果、不确定性和分歧 | 授予权限、修改预算、编造工具与保存回执；将自己的解释升级为作者原要求；自行批准采用或发布 |
| Codex Core：`codex-rs` | 通用会话、工具行动循环、上下文、压缩、协作与协议能力 | 小说关键词路由、章节规则、作品库、文学评价套路或产品UI策略 |
| Agent Engine：`agent-engine/src`、`agent-engine/native` | 通用模型接入、工具协议与校验、发现、执行身份、实际请求用量、取消及执行恢复 | 导入创作产品实现；判断情节应如何发展；另存作品正文或认定章节完成 |
| Electron Host：`novel-codex/electron` | 受信IPC、配置与凭据隔离、进程/会话生命周期、Runtime与Engine绑定、取消、事件消费、准入动作派发 | 按用户措辞选文学操作；另建规划器或模型循环；直改作品数据库；凭内存或模型话语认定已交付 |
| 工具执行适配器，包括Host媒体执行器 | 在明确授权、身份与额度下执行外部工具/媒体服务，返回真实产物、用量或错误 | 自行选择创作目标、扩范围、启动无界重试或把服务返回当作作品已提交 |
| Story Core：`native/story-core` | 作品/版本/候选、作者要求、领域授权、来源证据、事务、幂等、并发版本校验、Work额度、领域完成条件 | 调用模型来绕过校验；按文学偏好硬编码流程；将模型声明当作已发生事实 |
| Authoring：`native/story-authoring` | 基于领域事实构造任务、输入快照、上下文与写作契约 | 第二套作品事实、供应商循环、自行解释用户关键词或授权 |
| Runtime API：`native/story-runtime` | 认证、请求形状、调用领域用例、事务结果与事件传递；使用Engine通用证明合同 | 绕过Story Core写领域事实；复制一套文学决策或独立权限政策 |
| MCP：`native/story-mcp` | 真实工具schema、当前可见能力、可信调用身份、参数及结果传输、明确可纠正错误 | 直接访问作品数据库、直接执行供应商循环、丢弃业务结果只留诊断证明 |
| Renderer：`src` | 对话、阅读、编辑草稿、差异、作者操作、真实状态投影；调用公开应用接口 | 直接访问数据库、凭据、进程或模型；从答复措辞推断已保存/已采用/已完成 |
| Shared：`shared` | 跨层传输类型、不可变数据与无副作用的通用纯函数 | 依赖Renderer/Host/Engine；读取凭据、网络、进程或作品存储；成为隐蔽调度器 |
| 方法和角色资源：`codex-runtime`、共享目录、EternalLight来源 | 带来源和版本的可选创作方法、真实能力说明、角色职责建议 | 带入源工程的调度器/凭据/作品库；改变权限；要求每章使用固定方法和专家数量 |

存储职责允许各自持久化：UI草稿、Host连接配置、Codex会话历史、Engine执行账本与Native作品事实并非同一数据。禁止的是同一事实出现多个独立权威，不是禁止所有模块保存数据。

## 2. 必须保持的规则

### B01 依赖沿公开边界，类型也遵守

- Renderer依赖自身、Shared及浏览器库；Shared不反向依赖任何应用层。
- Host通过公开Engine导出和Runtime接口调用能力；不得深导入Engine私有实现、Renderer或领域数据库。
- Engine不得依赖小说/媒体领域实现，也不以源码导入方式嵌入Codex Core；Codex Core经明确协议和受控进程接入。
- Story Core不依赖Authoring/Runtime/MCP；Authoring可依赖Story Core；Runtime可依赖Story Core、Authoring与Engine的通用合同；MCP经Runtime接口访问领域，不直连Story Core/数据库。
- 测试可跨层验证真实合同，但生产代码不得借测试、fixture或构建入口绕过边界。生产所用支持模块也须扫描其传递依赖。
- 新共享类型归最低共同层。跨层重复定义必须生成或用合同测试证明一致；禁止复制后独立演进。

### B02 创作决策交给模型，确定性控制由工程执行

自由文本及完整上下文交模型理解，不能以“继续”“生成”“优化”等词硬选业务流程。显式按钮、结构化操作枚举、作者已选对象和已批准动作可以确定执行。

模型可用零个专用方法、零个子任务，也可改变计划或结束无价值分支。不得把“先规划→固定写手→固定审稿→重写”作为所有请求必经流程。独立核验等完成要求按适用产物与领域契约执行，不扩成普通问答也必需的团队流程。

### B03 一个领域事实权威，声明和回执分开

原始作者要求、模型解释、工作计划、候选正文、作者采用、发布、评估报告和领域完成必须分开。原要求有真实作者来源；模型可修正解释和计划，不能修改原话或降低标准掩盖失败。

准确定位、编辑、重开和交付所需的对象身份、修订、选区、素材引用及时间关系由领域合同管理。定位索引可从权威来源重建；人物关系、伏笔、镜头意图等派生语义保留来源、版本、覆盖及不确定性，不自动升级为作者设定。新增结构或字段须有实际编辑、交付或读取使用方，不因追求完整建模而成为默认必填项；已有作者要求和确认信息仍须保留。

保存由真实版本回执证明，采用/发布由对应作者授权动作证明，交付由适用领域条件与实际产物证明。模型结束回复、计划打勾、工具调用成功或子任务自称完成均不能替代。UI和Host只投影这些事实。

非必需分析失败不抹去独立已保存的成果，也不能被显示为分析成功；必需分析未满足时，相应目标仍为部分交付或受阻。程序校验、语义判断和作者满意分别说明证明范围，保留失败、费用及未知状态。

### B04 工具声明、模型可见内容与实际执行一致

能力目录只列真实资源，并区分当前可用、需要许可、不可用与仅有设计。必要的任务发起和状态入口应在当前授权范围内直接可见；领域能力可按需发现，发现不等于获得权限。

工具契约必须贯通声明→协议转换→模型输入→参数校验→执行→返回值。不得静默删除schema约束、把工具错误伪装成功、丢失业务正文/可纠正错误，或用简化fixture代替生产定义验收。协议确有约束表达限制时，必须显式声明该限制和最终校验责任，记录实际传输证据；不能宣称完整等值。

工具按明确意图组织，精简目录说明与按需指南须来自同一权威契约，并对应当前可见能力。减少重复上下文、冗余参数和大段回传时，保留完成操作及纠错必需的约束、版本、来源和回执；工具更少或载荷更短本身不证明更易用。项目、任务、会话等已由受信调用上下文确定的身份应由适配器绑定，不要求模型重新拼装授权凭据；模型提供业务意图及必要的目标对象、版本条件，冲突或伪造身份须拒绝。

跨进程、持久化和执行环境传递的数据按声明的协议值语义校验，不依赖对象引用相等或本地原型身份；仍须完整核对合同要求的字段，不得为通过序列化回读而删掉身份、范围或版本检查。

模型接入与切换还须核对消息角色和指令来源语义，接口接受 `developer` 字段不证明其保留开发者指令权限。协议适配方式随连接定义及资格指纹管理，切换不能沿用上一连接的隐含假设。供应商将指令降为用户文本时须显式适配或拒绝，并说明无法完全等价的层级限制；不得凭正文中的角色声明升级作者输入、引用或工具结果。验证实际供应商出站内容与必要的真实模型行为，不只检查 Core 入站字段存在。

信任边界可分别校验：IPC检查调用方和形状，Engine检查协议与通用参数，Native检查领域身份、范围和版本。禁止的是互相矛盾的定义和隐式跳过，不是删除全部重复校验。无法满足契约的工具应在调用前给出可定位的拒绝。

领域允许、当前请求已加载schema、上下文中曾提及工具是三个不同事实。按需隐藏/加载工具时，工具可见性与模型看到的发现说明必须同步；说明只引用当前真实可用的发现入口。未加载不能误称永久无权限，历史提及不能充当当前调用许可。不得猜测工具别名、自动扩大目录或强制模型使用某个可选方法来规避发现失败。

#### 防止把不同状态合并成一个判断

跨层契约须保留会改变后续行动的独立事实，不能以一个 `available`、`authorized`、`success` 或通用错误承载不同含义。按当前改动涉及的状态轴建模，不机械引入全局状态机或所有字段：

| 独立事实 | 不得据此推断 |
| --- | --- |
| 能力已安装、领域允许、schema已加载、供应商可用 | 其中一项成立不证明其余项成立；未加载不证明缺少授权 |
| 对象可读、可保存候选、可修改现稿、可采用、可发布 | 可读不授予写入；生成或保存不授予采用/发布；写操作权限失败不自动禁止合法读取 |
| 请求发送、执行终止、写入结果、费用结算、领域交付 | 传输失败不证明没有写入；费用未知不证明额度耗尽；保存不证明完成 |
| 可纠正、可立即执行、等待外部条件、需要作者决定 | 可纠正不等于可盲目重试；工程缺陷不等于需要作者授权 |

每项判断由事实所有者给出结构化原因及已核实证据。缺少证据时保留未知，不能仅凭工具名称、缺失列表项或供应商自由文本归因为权限拒绝。通用Engine只描述本请求的工具/协议事实；Native判定领域权限与保存状态；Host消费明确准入；UI只展示实际恢复状态，不自行推断原因或承诺恢复。

错误必须让接收方区分失败阶段、原始原因、已知副作用及允许的下一步。已有事实由原所有者引用，不复制成第二份账本。优先复用现有类型和结果契约；不得只增加解释文字而丢失机器可判定的原因。真正缺少作者授权时指出具体动作、对象和范围；仅缺schema时通过当前合法发现机制处理，不要求作者扩大权限。若无法判断，说明待核对项，不伪装成明确拒绝。

结构化错误必须穿过实际序列化边界并到达需要它的消费方。涉及 HTTP、MCP、IPC 或持久化时，验证来源、稳定原因、原执行关联及必要定位信息不会被压成 message；引用或参数拒绝应定位到具体对象或字段。来源由受信适配器赋予，不能因供应商正文包含本地错误名、JSON字段或自称来源而升级为本地事实。仅传递有消费需求的有界、脱敏字段，不为统一错误建立第二份领域状态。

本地绑定与参数预检拒绝、远端执行失败均遵循适用的结构化错误合同；本地拒绝没有远端执行记录时不得伪造关联，远端已有原因不得被通用包装覆盖。回归须经过真实结果封装和最终消费方，不能仅证明内部错误对象包含字段。

### B05 权限与预算贯穿一次工作

Native负责作者授权、领域范围与Work额度；Engine负责实际服务商请求预留、计量和结算。两者按真实task/work/budget/call身份核对，不能互相替代。

子任务、重试、恢复、换模型和更换方法继承原范围及累计用量，不清零费用，不扩大权限。模型提示词不能授予权限。采用/发布与保存候选分别授权；新用户确认仅在现有授权不足或真实意图冲突时发生，设计评审不自动要求再向用户请示。

作者额度上限、已确认消耗、在途预留与未知用量必须分别计量和展示；未设置上限不等于不记账，未知预留不等于实际收费或额度耗尽。输出无效不意味着供应商没有消耗：在权限、取消、时限和字节上限内独立收取并核对真实用量回执，幂等结算；不能为执行被拒绝而丢弃已可取得的用量，也不能为取回用量执行或展示已拒绝的输出。缺失回执保留未知；恢复设计须明确核对来源、准入条件与作者可理解的下一步，禁止清零、估算冒充实测或另建任务绕过原账本。

### B06 生命周期和恢复以持久事实为准

对话/任务应完成对应持久化与身份核对后再发布为可读取、可执行状态；内存创建不代表持久就绪。事件消费、结果提交、暂停取消及恢复须可重复而不产生重复副作用。

恢复先核对原身份、状态、版本、回执和账本，再将事实交模型决定后续创作；不伪造新作者输入，不偷偷重建任务或预算。未知写入必须先核对才能重试。历史未知费用保持原记录；正常创作默认仅计量，不要求作者填写请求数、token上限或有效期。未设置token上限时，已终止且完成费用登记的原attempt不因历史费用未知永久阻断原Work；后续attempt仍须通过写入、身份、来源、范围和生命周期准入。确有有限token上限时，未知费用不能被忽略。Engine同一未知请求不得重复派发。取消、暂停和真正阻塞不得被后台唤醒绕过。

错误类别由产生错误的边界确定，区分本地协议/输出校验、工具业务拒绝、供应商失败、传输失败、额度耗尽及用量未知；保留首个原因，不能被后续保护错误覆盖。确定性的本地输出拒绝不得默认按网络故障盲目重试；可重试性、是否已发送、是否可能产生副作用和用量是否已结算分别记录。供应商自由文本不能伪装成本地授权或预算结论；错误诊断限长脱敏，不记录凭据与无关正文。

首次观察到的失败与当前阻塞分别保留，并关联原执行；首次观察不自动等于根本原因。读取状态失败仅说明尚未取得事实，不能替代“待结算”“未知写入”或“额度耗尽”。写入与费用须可同时待核对，结算或保存后返回当前权威投影，不能继续返回操作前缓存的阻塞标签。

无进展保护必须说明比较的障碍、可信执行条件和实际进展。真实相关条件变化后可重新评估原 Work；错误换词、随机ID、时间戳、无关对象变动或模型自称已修复不能刷新重试机会，条件往返不能抹去原失败。纯协调回复不证明创作取得进展。重评仍须通过当前身份、授权、写入、预算、租约与暂停取消检查，不能凭旧停止标签永久锁死，也不能凭新条件直接授予执行。

后台核对或恢复失败必须有可查询的执行健康状态，说明关联任务、阶段、是否已安排重试及下次检查；退避及事件重复消费不得产生重复副作用。Host 健康描述获取事实或派发的能力，不覆盖 Native 领域状态。重开界面读取当前快照，Host 重启重新检查，不能沿用旧进程“正在重试”的承诺。仅有日志不算作者可见的故障处理。

### B07 开放工作区与协作不制造第二份真相

长篇资料按问题发现、分页和回读，引用真实对象、版本、摘要及范围。摘要用于导航，不能恢复授权或证明全文已经阅读；子任务读过不等于父任务读过。真正依赖变化才使结论失效，不能将无关变更一律扩成全书重审。

精确定位和编辑锚点由权威原文生成，声明坐标单位、来源版本与范围；重复匹配保留歧义，不擅自选中或用近似文本替换精确依据。定位命中、索引和片段读取各自只证明实际覆盖，不证明全文阅读或授予写权限。分页续读信息应可直接调用；游标、缓存和重试身份须保留所有影响结果及授权范围的查询、视图、对象与版本条件，不能串用另一查询的结果。

局部补丁复用现有领域保存事务、权限、版本比较、幂等与账本，不另建绕过校验的写入入口。减少模型回传全文不降低对原文匹配、重叠修改、锁定范围及未修改内容的保护；过期锚点或冲突返回可定位的拒绝，不能静默重新定位后写入。

原作可在授权范围内直接读取，语义分析按具体操作及证据缺口选择。每项准备条件须对应必需原作、制作输入、明确交付要求或实际消费它的操作；没有相关依赖的局部修改不以全书或全作品语义建模为前置。模型可在上下文中临时理解和整理，无需持久化每次推理；需要复用或被后续操作消费的结果按领域合同保存。一旦某项分析属于本次必需依赖，其存在、来源与有效性仍须核对；现行前置的修改遵循 B10。

子任务有明确目标、来源范围、权限、预算与结束条件。隔离候选通过领域提交合同整合，不能直接覆盖共享主稿。临时方法可自由创造；新程序工具或插件必须通过真实工具接入边界，不能由创作任务自行安装或修改应用。

### B08 UI按原因显示状态，保持阅读清楚

产品以对话驱动创作为主入口，默认围绕对话与当前作品阅读/预览组织；只保留有明确必要性的 UI。新增或调整任何入口、按钮、面板、表单前，须说明它解决的具体作者任务、现有对话或控件为何不足、是否与已有入口重复，以及能否复用、合并、按需展开或删除。不能因为新增领域能力或数据结构就增加一套界面，不能让作者操作固定向导来代替 agent 思考与规划。

专用 UI 用于直接编辑、空间/时间操作、差异比较及可信作者动作等有明确交互收益的场景；优先在当前作品或对话上下文按需呈现。减少 UI 不隐藏关键失败、真实状态、暂停取消及必要作者选择，不削弱可访问性或权限合同。已授权行为不增加重复确认；对话中的意图须经过既有可信身份与领域接口才能形成授权事实，不能靠模型声称“作者已确认”替代。

连接、运行时、历史读取、任务执行、保存、核验和作者采用分别投影。禁止把复合布尔值的失败统一解释为“模型不可用”。状态错误显示真实可恢复动作，保留输入草稿。

正文及有意义的进展在对话主线；工具诊断、ID、重试和校验细节按需查看。不得用重复“用户消息”展示内部接力，不从模型自然语言解析业务成功标志。不得为排查内部实现让作者填写技术参数。

全球化交流由作者意图优先决定，应用/系统语言偏好仅提供默认值；不得将某种语言设为全球固定默认，也不得按英文单词、字符比例或素材语言机械切换。模型区分交流语言、作品语言与原始引用，工具前提示、执行进度、子任务和最终解释遵循同一交流约定；明确双语需求及原文引用合法。语言规则传入模型不等于模型实际遵守，涉及语言体验的修复须分别验证首条进度、后续过程与最终答复，不翻译证据或重写已保存作品来掩盖展示偏差。

同一事实跨入口使用一致的展示语义，复用纯展示映射，不让各界面分别猜测恢复准入。“正在处理”“将自动重试”分别需要实际执行或已安排调度的证据；未知原因保留未知。错误和恢复回执须绑定正确项目、任务及对话；未绑定对话的合法任务也应能显示其失败，不能因空值表示差异吞掉提示，更不能将晚到回执显示到其他任务。

### B09 通用内核和外部方法有明确边界

**默认不修改 Codex 官方源码；例外必须先经开发者审核并明确同意。** 本规则覆盖本地 fork 中的官方来源代码（包括 `codex-rs/` 及其他上游维护文件），不只约束向官方仓库提交代码。优先通过现有公开接口、配置、应用层或 Agent Engine 实现需求；不得仅因底层实现更方便而修改官方实现。

确需本地修改时，先完成只读排查和可审核方案，说明问题证据、上层替代方案及其不足、拟改文件/符号、通用能力边界、验证计划、上游升级成本和补丁移除条件。必须取得开发者针对该方案及范围的明确同意，并在评审记录中注明审核者、同意依据和批准范围，之后才能修改；范围扩大须补充审核同意。普通“修复”“优化”“继续”授权、代理自审、测试通过或补丁登记均不能替代开发者批准。未获同意时继续可独立完成的上层工作，官方源码改动保持待审核；不得先改后请批，也不得借构建脚本、生成步骤或补丁注入绕过此规则。

下述官方更新流程用于引入官方原样实现，不构成本地自定义修改的豁免；若合并冲突解决需要改变官方实现语义，同样先取得上述审核同意。现有本地补丁不自动获得扩大或续改许可，也不因本规则新增而自动回滚；其保留、迁移或移除须单独评估并按涉及范围审核。

**官方库问题优先完整同步官方更新。** 遇到疑似 Codex Core 或其他官方依赖缺陷，先保留复现证据并核对当前依赖版本，拉取官方仓库目标分支的最新代码，默认完整合入该分支截至本次拉取的全部新增提交，再复验原故障，确认官方是否已经修复；不要先自行改写官方实现，也不得自行仅摘取相关修复提交或复制其中代码代替完整更新。记录官方仓库、目标分支、拉取时间、目标提交和合并结果，并验证目标提交已包含在合并后的提交历史中。合入前检查工作区状态与接口影响，保留未提交改动，不覆盖其他任务的工作。确有阻断导致不能完整合入时，记录具体原因和未完成范围；只有用户明确批准局部引入后，才可摘取提交或独立修复，并记录准确提交、范围与未引入部分，不能将局部引入宣称为全量更新。

官方更新合入后必须重新构建、核对构建身份，并验证原故障及受影响公开契约；启动/数据库问题必须从全新环境实测。拉取成功、合并无冲突或编译通过都不能替代故障复验。没有官方修复，或官方更新经验证仍失败/存在明确阻断时，才能评估最小本地补丁，记录未采用官方更新的证据、职责边界、回归与未来移除条件。不得通过放宽校验、清空失败记录或替换用户数据掩盖问题。

产品需求优先在领域、Host和Engine公开接口内实现。经开发者审核同意修改Codex Core后，仍必须证明属于通用能力，在现有 `codex-runtime/upstream-patches.json` 登记动机、路径、符号、测试与基线；继续通过现有Fork门禁。登记与门禁不能替代事前批准，不能因为写在Core里就认为小说业务正确。

EternalLight及其他方法按来源和适用问题接入，不导入其运行框架、账号或作品库。方法提供建议；执行身份、权限、费用及作品事实由本工程负责。

### B10 每次改动都要有责任归属和对应证据

动手前在现有改动评审中填写：责任模块/适用规则、读取与写入的事实权威、经过的公开契约、为何不放邻层、影响的调用方与失败路径、所需验证。涉及结构或准备条件时，说明目标对象、必需原作、确定性检查及派生分析的实际使用方；只审查本次操作及直接受影响的链路，不要求先完成全工程审计。一个连贯改动用一份评审即可，新增必需调用方同步不需要另开一套方案。

**修复前先判断是设计缺陷还是实现缺陷。** 根据实际触发、预期行为、现行设计/契约及执行证据，记录“实现缺陷 / 设计缺陷 / 两者兼有 / 证据不足”及判断依据。实现缺陷指设计能合理满足要求，但代码没有正确实现；设计缺陷指即使代码按设计执行，职责划分、数据/状态模型、接口契约或流程仍不能满足要求。不能因为代码符合现有文档就认定设计正确，也不能仅凭故障出现的位置确定责任层。证据不足时先定位和验证，不把推测记为已确认根因；涉及官方依赖时同时遵循B09。

实现缺陷在正确责任层按合理设计修正；设计缺陷必须评估结构和设计优化，说明目标职责、事实权威、状态/契约及受影响调用方，并在本次修复范围内完成消除根因所必需的调整。两者兼有时同时修正设计和实现。不得仅在症状出现处叠加特判、重试、兜底或绕过校验，维持已确认错误的设计；若评估后无需结构调整，应说明根因如何通过现有结构得到解决。

修复范围以消除根因和保持相关链路一致为准，不以改动行数最少为目标，也不借局部故障扩大为无依据的全工程重构。结构调整同步相关契约、调用方、测试与现行文档，并遵循当前零兼容策略。若确需先止损，记录保护范围、尚未解决的根因及后续完成条件；止损不能标记为根因修复完成。后审依据原故障、受影响的同根因路径和必要拒绝边界，核对修复是否消除根因，而非仅使当前样例通过。

涉及状态或权限的修改，评审必须提供一张仅覆盖受影响组合的判定表：输入事实及来源 → 允许/拒绝/待核对 → 是否有副作用 → 自动下一步或作者动作。先列容易混淆的反例，再实现成功路径。例如“有读取权限但无写权限”“领域允许但本轮未加载”“请求中断但已保存”“未知费用且无额度上限”“重复事件遇到作者暂停”。不能只测全部允许和全部拒绝两个极端，也不能只测试错误文案。

回归沿真实公开合同验证生产者、传输、消费者和UI使用的状态；断言包括拒绝调用零执行、已保存成果保留、费用不清零、原任务身份不变，以及暂停/取消不被自动恢复绕过。只要求与本次修改相关的组合；沿同一原因检查相邻调用方，避免每遇到一个表现才修一个入口。架构静态门禁只能证明依赖边界，不能替代这类行为证据。

测试必须观察当前实际使用的实例、适配器和持久结果，不能以未被调用的旧对象上的mock或spy证明行为。序列化相关修复须包含真实往返及受影响的拒绝反例；测试失败先核对生产路径与断言合同，只有证据确认fixture过期才调整，不能将真实缺陷归为测试维护问题。

涉及授权、预算、事实权威、生命周期、工具契约、模型决策或跨层依赖的改动，必须完成五视角前审和后审。其他代码/UI/配置改动仍遵循项目现行评审门禁，可使用精简表。五视角不等于必须启动五个额外模型。评审须注明实际执行者及方式（自审或独立复核），每个视角的结论关联可定位的方案、实现或验证证据；前审计划不能冒充后审结果。条件批准列明待满足条件及关闭证据，无适用影响说明理由；未执行的检查不记为通过。

新接口或行为改变同步生产者、消费者、类型、生成资源、测试和现行文档；不得靠旧字段fallback、放宽断言、跳过失败、清掉失败样本或降低安全/交付标准获取绿色。开发阶段直接形成一套目标实现，并在同一改动中删除被替代的旧分支，不增加过渡兼容或双轨运行；适用范围由当前零兼容策略决定。

允许经评审移除无必要的实现前置，或改用原作直接核验；评审须说明新旧条件的依据，以及作者要求、安全边界、来源约束和交付标准如何保持。变更一次性同步受影响的创建、准入、读取、报告、完成终验、恢复、类型、测试和文档；文档修改不能使尚未修改的程序跳过现行检查，完成后的程序只执行新的当前合同。历史失败记录保留，新合同下的结果另记，不把删除旧前置写成旧任务已经成功。

每个已确认的真实故障必须闭合“实际触发与失败证据→责任模块和根因→职责/契约修正→对应回归→受影响应用路径再验”。修复评审须标明故障与回归的映射；相同根因的多个现象可以共用有意义的用例，不能只改报错文案、添加无关测试或以总测试数代替验证。回归使用真实公开合同复现原失败条件，并验证修复后的行为；涉及权限、来源、预算和恢复时，覆盖受影响的拒绝边界。保留原失败及当前源码/构建身份，不为掩盖失败削弱作者要求、安全边界或交付标准。应用入口故障仅凭静态/合同测试不能宣布闭环；实际再验尚未完成或仍有阻断时，明确登记剩余项。测试按影响范围选择，不机械扩大为全量重跑或付费模型调用，不让作者追加内部技术参数或指令代替应用纠错。

修复错误分类、流式输出或结算问题时，沿同一失败边界检查相邻错误类型与协议路径，不能只覆盖首个报错字符串。按影响范围覆盖JSON/流式、终止帧、真实用量存在/缺失、取消/超时、拒绝内容零执行及幂等结算；未复现的源码风险单独标记，不冒充真实故障或已修复。

从故障吸收开发规则时，提炼事实权威、状态区分和可验证的不变量，优先补充现有条款与评审模板；不逐项复制故障清单，不把某次修复的阈值、字段名或固定创作流程升级为通用政策。规则、代码实施、构建加载、应用验收分别标明状态；规则新增不会自动改变运行时行为，尚未完成的场景仍保持未完成。

## 3. 每次改动如何验收

| 改动范围 | 必须具备的证据 |
| --- | --- |
| 仅规则、说明或评审文档，未改变程序行为 | 核对事实、条款与引用的一致性，检查链接、结构和改动范围；不冒充运行验收，不要求重跑应用或付费模型 |
| 所有生产代码/接口改动 | `npm run architecture:check`、对应评审；新增文件同样检查，不只扫描diff |
| 类型/纯函数/展示 | 对应类型检查或受影响的行为验证；不要求调用付费模型 |
| 工具/schema/能力目录/协议转换 | 使用真实生产目录和真实转换器验证；覆盖必要正例、拒绝负例及结果/错误，不只mock接口形状 |
| 权限/预算/保存/恢复/生命周期 | 真实边界合同验证，覆盖取消、越权、重复、未知状态或版本冲突中受影响的情况 |
| 用户创作路径 | 从实际应用入口验证受影响场景；自动化受控provider与真实模型证据分别记录 |
| 通用共享执行合同、跨层整体集成或发布 | 完整相关回归与既有Fork/发布门禁；本地已绿且源码未变化的相同检查不无理由反复运行 |

限制须说明其保护对象、证据、责任层、计量单位及触发后的恢复方式。作者授权、保存一致性和供应商真实容量边界必须保留；缺少依据的请求数、步骤数、总时长或独立字段长度不得代替作者任务目标。单次容量不足优先通过分页、分段、压缩或同一Work内接续解决，保留原要求、累计用量和已保存成果。同条件无进展、未知写入等暂停必须返回具体原因和可恢复状态，不能伪装完成或要求作者填写内部技术参数。新增硬阈值须在评审中说明为何现有完整请求容量、权限或一致性校验不足，不能以“已有常量”作为必要性依据。

采用“影响范围→最小有意义验证→必要时整体验收”。不要求所有小改动都重复 `verify`、完整Native和真实付费模型；引用既有证据须说明源码/构建身份和适用范围，新的改动不能冒用旧证据。

真实创作验收保留一句简短输入：应用自行理解、组织、保存、检查及交付。验收者不逐步指导模型或代替应用修稿；失败保留，生产修复后的再测另记样本。单章成功只证明该场景，不证明长篇稳定性、全部媒介或文学质量。

### 工具效率与评测证据（涉及评测或效率声明时适用）

- 对照使用可比任务、输入、授权、来源读取义务和正确性标准，先验证产物及受保护内容，再比较开销。记录源码/构建身份、模型与配置、样本范围及计量口径；分别报告首次成功、纠错与全流程成本，不只挑最省的一次保存。
- 确定性合同样本、受控provider的应用路径和真实模型行为分层报告。本地token估算注明分词器、载荷范围及未包含的上下文；不能将字节减少等同token减少、估算等同实际收费，或将受控调用证明为模型自主成功。用量缺失保留未知，环境准入失败属于尚未测得模型行为，不计作模型成功或零消耗。
- 多样本评测须持续保留一致、可恢复的阶段证据：运行开始及样本状态变化可追溯，中断后仍可取得已持久化结果，并将未确认完成的样本保留为在途或未知；失败、超时、中断、未启动和结果未知保持可区分，不能只留下成功样本。可采用原子文件替换、事务或可恢复的追加日志，须验证所选方式的中断一致性，不限定存储实现。明确预期样本身份、数量与各指标分母，缺失或重复不得冒充完整通过。评测须有明确运行预算、取消和资源清理，复用生产执行链路，不另建供应商行动循环。
- CI先检查样本完整性和正确性，再检查有依据的效率回归；失败时也保留可取得的报告。阈值注明适用负载、计量范围和噪声处理，不将单次实验常量升级为生产限制；本地通过、远端CI通过和外部模型验收分别记录，未执行或受阻项仍为未完成。
