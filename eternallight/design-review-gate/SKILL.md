# Design Review Gate

在当前工程中，所有代码修改都必须先经过“方案设计—多角色评审—实施—复核”流程。本 Skill 适用于新增、修改或删除代码、配置、接口、数据库/数据结构、构建脚本、测试、Electron 主进程/渲染进程和 UI/UX；纯文字说明且不改变契约或行为时，可以只做简化方案记录。

## 核心门禁

不得跳过方案直接修改代码。每个变更必须留下可追溯的评审记录，并由以下五个角色分别评审：

1. 架构专家：系统分层、模块边界、领域模型、数据契约、集成方式、可演进性、扩展性和技术债务。
2. 技术专家 A：依赖、数据流、可靠性、安全、性能和可运维性。
3. 技术专家 B：实现可行性、代码可维护性、兼容性、迁移、边界条件和测试覆盖。
4. 产品经理：用户价值、问题定义、范围、优先级、验收标准和失败场景。
5. UI/UX 设计师：信息架构、交互流程、状态设计、文案、可访问性和视觉一致性。即使本次没有 UI 影响，也必须由该角色明确记录 `N/A` 及理由。

这些角色可以由独立的子任务完成；如果当前环境没有多代理能力，必须在同一上下文中进行五个相互隔离、明确标注的评审轮次。不得把单一判断伪装成真实外部专家意见，也不得声称有真人参与。架构专家不得由技术专家 A 或 B 的结论隐式替代；没有独立架构结论时，评审门禁不算完成。

## 工作流程

### 1. 识别变更与读取上下文

- 明确目标、非目标、用户和验收结果。
- 检查仓库状态、相关模块、现有约定、测试、构建方式和既有设计文档。
- 标出受影响的文件、公共 API、持久化数据、平台行为和 UI 表面。
- 需求不完整时，优先做不改变意图的合理假设并记录；只有无法安全推进的关键歧义才向用户提一个阻塞问题。

### 2. 编写方案

方案至少包含：

- 背景、问题、目标和非目标；
- 当前行为与受影响范围；
- 候选方案、取舍和选择理由；
- 推荐方案的架构、模块边界、数据流/控制流和错误处理；
- 文件、接口、配置、数据结构和迁移变更；
- 安全、性能、跨平台、可观测性和回滚风险；
- 测试策略、验收标准和发布/恢复计划；
- UI 变更涉及的页面结构、交互状态、空态、加载态、错误态和无障碍要求。

小改动可以使用精简方案，但不得省略影响范围、风险、测试和四角色评审。推荐使用 [review-template.md](references/review-template.md)。

### 3. 执行五轮评审

将同一份方案分别交给五个角色审查。每个角色必须输出：

- `APPROVE`、`APPROVE WITH CONDITIONS` 或 `BLOCK`；
- 发现的问题及证据；
- 严重级别 `P0`（必须停止）、`P1`（实施前必须解决）、`P2`（应改进）或 `P3`（建议）；
- 可执行的修改建议和责任归属。

评审重点：

- 架构专家关注长期架构、边界、契约、演进和系统性耦合，不只检查当前实现是否可运行。
- 技术专家 A 关注依赖、可靠性、安全、性能和可运维性，不重复承担架构专家的独立结论。
- 技术专家 B 关注能否可靠落地，要求测试、兼容和迁移方案具体可执行。
- 产品经理检查方案是否解决真实目标，防止范围膨胀，并把验收条件写成可验证结果。
- UI/UX 设计师检查完整任务流，而不只看静态页面；必须覆盖首次使用、空数据、加载、错误、成功、撤销和键盘/辅助技术场景。无 UI 影响时记录 N/A，不得默认为通过。

### 4. 综合决策与实施

- 在任何代码修改前，解决全部 `P0` 和 `P1` 问题。
- 五个角色都必须为 `APPROVE`，或为 `APPROVE WITH CONDITIONS` 且所有条件已记录为实施任务和验收项。
- 对架构、产品范围、数据迁移或用户流程存在未解决的重大取舍时，暂停并请用户决策；不要擅自选择会改变目标的方案。
- 实施时保持变更与已批准方案一致。若发现需要实质性偏离，先暂停，更新方案并重新评审受影响的角色。

### 5. 实施后复核

- 按风险执行格式化、静态检查、单元/集成测试、构建和必要的 UI 验证。
- 复查最终 diff，确认没有越过非目标范围、破坏现有行为或遗漏文档/迁移。
- 把测试结果、偏差、剩余风险和后续工作写回评审记录。

## 对外输出格式

在开始修改前，先给出简明方案和五角色评审结论；不要只说“已评审”。实施完成后说明：

1. 采用的方案和关键取舍；
2. 五个角色的结论及已解决条件；
3. 修改的文件/模块和用户可见变化；
4. 验证命令及结果；
5. 未解决风险或需要用户决策的事项。

详细记录模板见 [review-template.md](references/review-template.md)。
